Pattern · Profile Photos

Write the new file, keep the old one, move the pointer

The technical name for this is append-only (versioned) storage with a mutable pointer. Nothing is ever overwritten on disk — a fresh upload always becomes a brand-new file, and only one small database field is updated to say "this is the current one."

Analogy: think of a library that never throws away an old edition of a book. When a new edition arrives, it goes on the shelf next to the old one, and the catalogue card is updated to say "the current edition is over here." The old copy still physically exists in the archive — it's just no longer what the card points to.

What happens, in order

  1. Traveller opens their profile and picks a new photo. The form sends the file to the /profile route.
  2. The server checks the file is safe to accept — a real image type (PNG/JPG/JPEG/WEBP) and under 3 MB.
  3. A brand-new filename is invented, built from the traveller's user ID plus the exact millisecond of the upload — so it can never collide with any file that came before it.
  4. That file is written to disk under its new name. The previous photo file is not touched, moved, or deleted — it simply stays where it was.
  5. Only the database is updated, setting the traveller's avatar column to the new file's path. This single row is the only thing that changes "which photo is current."
  6. The profile page re-reads that column and displays whatever path it currently holds — which is now the new photo.
In one sentence "The new one replaces the old one" is true from the user's point of view (they only ever see the latest photo) but not true on disk — the old image file is still sitting in static/uploads/avatars/, just with nothing pointing at it anymore.

Pattern · Booking Dates

No traveller can be in two places on the same day

This is a classic date-range overlap check. Before a booking is allowed to save, the server works out which calendar days the new trip would occupy, compares that range against every trip the traveller already has, and blocks the booking if even a single day is shared.

Analogy: it's the same check a hotel receptionist does with a paper diary — before writing in a new reservation, they run a finger along the existing bookings for that guest to see if any of the days are already inked in.

Worth telling your supervisor The overlap check only looks at this one traveller's own bookings — it has nothing to do with how many seats a package has, or whether other travellers are booked on the same dates. It purely stops one person from accidentally (or fraudulently) holding two trips on the same day.
